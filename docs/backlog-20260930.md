## Audit findings and changes

### Canonical execution

The effect planner could identify repeated leaf references, but the UI could still
execute them through multiple composite owners. In particular, a second Restore
could consume the same snapshot twice or incorrectly fall back to defaults.

`CatalogExecutionBatch` now shares one result per canonical backend type, stable
ID and operation within a selected batch. In-flight results, failures and exceptions
are shared too. Composite execution uses the original leaf backend rather than an
independent wrapper write path. A fresh batch starts without stale cached results.
Apply, explicit OFF, exact Restore and default Restore remain distinct operations.

Existing IDs and backup formats are unchanged. This does **not** merge conflicting
original snapshots or every overlapping registry primitive. Essential Telemetry's
advertising/personalization values and their separately owned Advanced controls
remain a known overlap, blocked by declared-effect preflight when selected together.
This conservative ownership check now also guards bulk Restore and explicit OFF;
it rejects ambiguity rather than choosing an original snapshot arbitrarily.
Broader metadata coverage, snapshot migration and non-catalog/profile consolidation
remain necessary. No full-system deduplication claim is made.

### Storage / Windows Servicing

The new Advanced panel provides:

- Optional-feature and capability inventory, A–Z, with explicit current states.
- Individually confirmed feature Enable/Disable and capability Install/Remove.
  Feature disable retains payload; capability removal may require installation
  media or Windows Update to undo. No automatic `/All`, `/Force` or dependency
  enabling is used. A stale selection or unknown pre-state blocks mutation.
- Durable before/after TXT evidence and exact command arguments. An exit code alone
  is insufficient for feature/capability verification. Pending states and 3010 are
  reported as requiring restart, not as verified running behavior.
- Component-store analysis and normal cleanup, separate from typed-confirmation
  ResetBase. **ResetBase prevents uninstalling existing updates; logs cannot undo it.**
- Third-party driver inventory and export to a new unique local folder. Reparse
  ancestors are rejected; export checks do not follow reparse subdirectories.
  No driver deletion, force removal or automatic age-based decisions are provided.
- Read-only Reserved Storage, CompactOS and Windows RE information. Existing
  hibernation/reserved-storage controls are not duplicated with competing owners.

Operations use the shared SystemMutation / WindowsServicing lease and invalidate
old catalog scans before and after an attempted change. Live servicing mutations
are not killed on a short timeout. No command automatically reboots the PC.
Cleanup reports Windows analysis, not a fabricated byte-saving estimate.

### Individual security evidence and HVCI

Advanced → Security & Mitigations reports local HVCI configuration separately from
Win32_DeviceGuard configured/running services, VBS state and hardware capabilities.
The native SAFEARRAY reader is AOT-compatible. Management indicators are conservative
evidence, not a definitive active-enrollment diagnosis.

Enable/Disable HVCI and Restore exact snapshot are implemented. All writes require
explicit user confirmation, administrator rights, supported client Windows, complete
evidence, no management/policy indication, explicit unlocked values, and no active
or unknown Code Integrity policy. Enable additionally requires already-running VBS
and virtualization hardware evidence. Unknown conditions block local mutation and
offer Windows Security for review; there is no organization/UEFI bypass.

The first original Enabled DWORD or value absence is durably saved before mutation.
Restore never guesses a missing snapshot. Registry readback is **configuration**
verification only: restart and reload are needed to inspect effective protection.
No hypervisor/BCD, TPM, Secure Boot, firmware or generic CPU masks are changed.
No performance benefit has been measured. Other existing security managers remain.

VBS, Credential Guard and hardware stack-protection statuses are read-only here.
Their mutation controls, LSA/Exploit Protection controls, CPU-specific mitigation
verification and a complete audit of Firewall/SmartScreen/UAC are **not completed**.

### Offline Image Workspace

The workflow uses a user-selected local `.wim` and existing workspace parent:

1. Inspect available indexes; validate detailed version, edition, architecture and
   Client installation. Unknown, Server/WinPE and pre-19041 targets are rejected.
2. Create a unique owned workspace, copy the entire source read-only, and verify
   SHA-256. Check a conservative free-space floor (twice WIM size plus 10 GiB).
   This floor is **not a guarantee** of enough space for all images or exports.
3. Recheck clone metadata/hash before mount. Require DISM's exact clone path,
   selected index, mount path, read/write permission and OK status before servicing.
4. Inventory and select a conservative allowlist of removable features,
   capabilities and provisioned apps. Fresh pre-state must match selection.
   Per-item planned/verified changes and DISM outputs are retained in the workspace.
5. Optionally analyze/clean the copy using supported component cleanup, no ResetBase.
6. Explicitly Commit or Discard and confirm that no owned mount remains registered.
   Export a committed index into a **new** `optimized.wim` (index 1).

No original WIM, live Windows, ISO, ESD, VHD, arbitrary driver/package deletion or
direct WinSxS removal is targeted. Export metadata is not proof of boot compatibility.
There is no per-item Undo; retain the original and test the result in a VM.

Every session retains `session.json`, source hash, target identity, change history,
state, DISM process identity and separate command logs. Live servicing is not killed
on timeout. Closing an idle dialog does not delete/discard its mount. Reopen and
load the manifest to reconcile it. Active recorded DISM processes block recovery;
unknown/interrupted changes block Commit and further removals. Non-OK mounts require
manual Microsoft DISM recovery; the utility does not clean unrelated mounts.
